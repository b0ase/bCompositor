# bCompositor Roadmap

bCompositor is a Bitcoin (BSV) fork of [Compositor](https://github.com/robbietilton/Compositor), the MIT-licensed native macOS Photoshop alternative by Wonder Assembly LLC (keep their copyright notice in `LICENSE`).

Fork: https://github.com/b0ase/bCompositor. `origin` is this fork; `upstream` is robbietilton/Compositor (`git fetch upstream && git merge upstream/main` to pull in their work).

Guiding principle: the Bitcoin features should be things **only the editor can do**, because only the editor knows how an image was made. Export-to-ordinal alone is not a reason to switch editors.

## 1. Versioning: the BIG feature

Save projects progressively, git-style, as in Bitcoin-Writer (bWriter). A "git file" is a **magnet-style link** that lets someone open, edit and fork a project's history.

The design is still being worked out; see the Versioning section below.

## 2. Provenance / proof of authorship

The editor knows the source images, every layer, every adjustment, and whether generative tools (Content-Aware Fill, Remove Background) were used.

- [ ] On save or export, sign a hash of the edit history and timestamp it on-chain
- [ ] Result: a verifiable record saying "made by this identity, from these sources, with these edits, no AI fill"
- Like C2PA / Content Credentials, but with no dependence on Adobe's servers

## 3. Proof of prior art

- [ ] Timestamp each saved version of the layered project on-chain, to settle copyright disputes over who had it first
- Largely falls out of #1 (versioning)

## 4. Ordinal export

- [ ] Export as a 1Sat Ordinal, with the provenance record attached
- [ ] Default: inscribe a web-sized render plus a signed hash of the full-resolution original. Full-resolution inscription is optional because of cost.

## 5. Layer lineage and royalties

- [ ] A layer can itself be an ordinal
- [ ] An exported composite records which parent inscriptions it was built from
- [ ] Sales route part of the proceeds back to the creators of those layers
- Unique to a compositing tool: the "Compositor" name fits

## 6. Asset and licence marketplace

- [ ] Brushes, presets, LUTs, templates and stock layers sold as tokens and usable inside the app
- [ ] Sell usage licences as tokens rather than one-off NFTs (closer to how stock photography makes money)

## 7. Pay-per-use cloud features

- [ ] If any feature needs cloud compute (better Select Subject, upscaling, generative fill), charge micropayments per use rather than a subscription

## Wallets

Compositor is a native Swift app, not a web app, so browser wallet code does not port directly.

### Version 1

1. **Metanet Desktop (BRC-100): the main wallet**
   - Call its JSON API directly over HTTP on `localhost:3321`
   - Write a thin Swift client covering only the calls we need (`getPublicKey`, `createSignature`, `createAction`)
   - The wallet builds and funds transactions itself; for inscriptions we supply the locking script
   - Always connect to Metanet Desktop explicitly: bitsign found that `@bsv/sdk` auto-detection (`'auto'`) prefers `window.CWI`
2. **HandCash Connect: identity, pay and `signData`, not token custody**
   - The app secret cannot ship inside an open-source binary, so HandCash login needs a small server
   - The server redirects back to the app through a `bcompositor://` link
   - **This is a separate bCompositor service, not bitsign or bChat's backend (decided 2026-09-23)**
3. **Built-in token wallet: where HandCash users' tokens live** (based on bitsign's `lib/bit-sign-wallet.ts`)
   - Generate one random key per HandCash handle. Never derive it from HandCash `signData`: that output is non-deterministic, and bitsign stranded funds this way.
   - Store the key in the macOS Keychain
   - Require the user to download a backup before continuing
   - The backup file uses bitsign's `bit-sign-wallet-backup` v2 JSON format, so the same file works in both apps
   - To avoid re-implementing Bitcoin cryptography, run `@bsv/sdk` and `@1sat` inside JavaScriptCore rather than rewriting them in Swift
   - Keep this wallet even after HandCash adds tokens; it also serves users who have no wallet

### Later

- **Yours Wallet:** extension-only, so it would need a localhost bridge page. Its `sendBsv` also hangs on `/proof` (yours-wallet#313).
- **MetaMask and Phantom:** not needed

### Patterns worth copying from bitsign

- A capability table saying what each wallet can do (`canSign`, `canPay`, `whyNot`), from `signing-wallets.ts`

### What bmovies taught us

- It never built a HandCash token wallet
- It trusts the transaction ID the client reports
- It has no signing abstraction

Don't copy these gaps.

## Versioning design (draft)

### What bWriter does

Source: `/Volumes/2026/Projects/bitcoin-writer`, see `UTXO-CHAIN-SPEC.md`.

- **Commits are chained by spending coins.** Save N spends save N-1's 546-sat "chain UTXO", so history order is enforced on-chain.
- **A fork is a transaction with two outputs**, one per branch.
- **Document ID = the genesis txid.**
- **Write access = holding the chain UTXO.**
- **Every save stores the whole document**, as encrypted B:// data in OP_RETURN with a CHAINPROOF MAP record.
- **Limits:** 1 MB per save; single-user only; encryption keys are derived from HandCash; no merge, no sharing, no magnet link.

### What bCompositor keeps

- The UTXO chain of proof: enforced ordering, a fork as two outputs, and write access as holding the chain UTXO

### What bCompositor changes

**1. Commits carry hashes, not images.** Compositor projects are already git-shaped: a `manifest.json` plus one PNG per layer and per mask (`ProjectStore.swift:111`).
- Each layer and mask is content-addressed by hash.
- A commit is a tree: the manifest with blob hashes in place of filenames.
- On-chain, a commit holds `tree_hash`, `parent`, `genesis`, `version`, the author's signature, and a small encrypted tree.
- Unchanged layers are never stored twice.
- Hashes must be of pixel data, or only changed layers re-encoded, because PNG re-encoding can change bytes when nothing has changed.

**2. Real merges.** Layers have stable UUIDs, so a three-way merge of the manifest works at layer level.
- Branch A edited layer X and branch B edited layer Y: merge automatically.
- The same layer changed on both branches is a conflict: keep both as two layers, or pick one.
- A merge commit spends both branch tips (two inputs).

**3. The magnet link.**

```
bcomp:?xt=urn:bsv:<genesis_txid>&tip=<txid>&ws=<blob source>…#k=<read key>&w=<write key>
```

- `xt`: the genesis txid, which identifies the repo (like a torrent's infohash)
- `tip`: optional; pins a particular version
- `ws`: one or more places to fetch layer files from. Every file is checked against its hash, so an untrusted source is fine.
- `#k`: the repo's read key, in the fragment so it never reaches a server
  - One random key per repo, **not derived from HandCash** (bitsign's lesson)
- `#w`: optional write key that controls the chain UTXO
  - A link with `w` is an **edit link**; a link without it is a **view/fork link**
  - Two holders of an edit link saving at once race: the first spend wins, and the other client rebases, which is the equivalent of git's rejected push
  - Anyone with a view link can fork: they start their own chain whose genesis references the parent commit

**4. Signed commits.** Add an AIP or SIGMA signature from the author's identity.
- bWriter's `author` field is unsigned, so this also covers provenance (roadmap #2).

### Decisions (2026-09-23)

**Blob storage.** By default, layer files go to **our own hash-addressed store** (S3/R2).
- Putting a version on-chain is optional: B://, with BCAT for files over 1 MB.
- WebTorrent seeding may come later.
- The link's `ws` list can mix sources, because every file is verified by hash.

**Write access.** Collaborators use their **own wallet keys by default**. Bearer edit links are opt-in and revocable.
- **The chain UTXO is locked to a 1-of-N script:** the owner's key OR any collaborator key OR any active invite key.
- **Adding a collaborator:** the owner adds their identity key, handle or paymail. The collaborator then saves with their own wallet, and each commit is signed by the person who made it.
- **Edit links:** these are opt-in. `#w` carries an invite key that the script also accepts.
- **Revoking access:** the owner makes a save that re-locks the chain UTXO to a script without that key. This works for a leaked link and for removing a collaborator.
- **Ownership:** only the owner key can change the script, so the owner can never be locked out.
- **Why not bearer-only:** a leaked link would give edit rights forever, and every commit would be signed by the same anonymous key, which would weaken provenance (#2).

### Still open

- The `bcomp:` URL scheme needs registering with macOS so that links open the app.
- Which script template to use for the 1-of-N lock:
  - bare multisig (1-of-N `OP_CHECKMULTISIG`)
  - a custom sCrypt contract
  - a hash-list with `OP_IF` branches
